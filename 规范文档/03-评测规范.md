# 03 · 评测规范

> 目标：用可重复的题库与指标证明「场景成立、链路正确、优化有效」。  
> 门禁脚本：`scripts/run_eval.py` + `backend/tests/eval/cases.yaml`  
> 版本：v1.0 · 2026-07-16

---

## 1. 为何必须评测

没有评测的 Agent 项目只能演示「碰巧答对」。评审要看：

- 有据问答是否稳定命中  
- 无依据是否稳定拒绝（反幻觉）  
- 工具是否在该调时才调  
- 优化是数据驱动还是凭感觉  

原则：**改路由 / Prompt / 检索前后必须跑评测；结果归档基线。**

---

## 2. 题库规模与节奏

| 阶段 | 规模 | 说明 |
|------|------|------|
| T1 | ≥ 3 条金标准 | 命中 / 缺失拒绝 / 引用格式，立刻进 `cases.yaml` |
| T3 | ~50 条 | 覆盖下方五大类 + 工具 / 降级 |
| 后续 | ~100 条 | 加多轮、歧义、边界与回归锁 |

本阶段（文档 T0）交付分类定义 + 示例草案；**不要求一次写满 50 条进 YAML**。

---

## 3. 题库分类（五大类 + 扩展）

| category | 含义 | 典型期望 |
|----------|------|----------|
| `hit` | 单轮制度命中 | `expected_intent=local`；命中指定标题；答案含引用 |
| `multi_turn` | 多轮追问 | 后轮仍围绕同一制度主题（可用 notes 描述；实现可先单轮近似） |
| `ambiguous` | 歧义问题 | 「报销上限」→ 需澄清或按默认制度检索，不得乱答 |
| `missing` | 知识缺失 | 明确拒绝；禁止编造数字 |
| `oos` | 超范围 | 不伪造制度；可拒答或引导 |
| `tool` | 工具类 | 时间 / 计算 / 学习意图正确 |
| `degrade` | 降级路径 | Mock、熔断、空结果、开关关闭行为 |

## 4. 用例字段约定

在现有 YAML 字段上扩展 `category`（建议字段；runner 可先忽略未知键）：

```yaml
cases:
  - id: policy_reimburse_cap
    category: hit
    query: "差旅住宿费上限是多少？"
    expected_intent: local
    must_hit_title_any: ["差旅报销制度"]
    must_answer_contain_any: ["**参考**", "500"]
    must_answer_match_any: ["document_id="]
    forbid_phrases: ["【直接回答】"]
    notes: "库内需预置差旅报销制度样例"

  - id: policy_missing_overseas_medical
    category: missing
    query: "海外医疗险报销比例是多少？"
    expected_intent: local
    expect_max_hits: 0
    must_answer_contain_any: ["不足以", "暂无", "补充"]
    forbid_phrases: ["一般为", "通常是", "估计"]
```

### 字段说明

| 字段 | 用途 |
|------|------|
| `id` | 稳定主键，禁止随意改名（改名需记基线） |
| `category` | 分类统计命中率 |
| `query` | 用户输入 |
| `expected_intent` | 路由断言 |
| `must_plan_step` | 计划中须含某工具步 |
| `must_hit_title_any` | 检索标题命中 |
| `expect_min_hits` / `expect_max_hits` | 命中数量门禁 |
| `must_answer_contain_any` / `all` | 答案子串 |
| `must_answer_match_any` | 正则或特殊模式（如 `document_id=`） |
| `forbid_phrases` | 禁止出现的幻觉 / 错误格式 |
| `check` | 基础设施类（上传上限、熔断、向量开关等） |
| `notes` | 前置数据、已知限制 |

## 5. 指标定义

| 指标 | 计算 | 目标（建议） |
|------|------|----------------|
| **回答命中率** | `hit` 类 PASS / `hit` 类总数 | T3 ≥ 80%，后续 ≥ 90% |
| **缺失正确拒绝率** | `missing` 类 PASS / `missing` 总数 | ≥ 95%（宁可不答不可瞎答） |
| **超范围正确处理率** | `oos` PASS / `oos` 总数 | ≥ 90% |
| **工具调用成功率** | `tool` 类 intent/step 断言 PASS | ≥ 95% |
| **整体门禁通过率** | `run_eval` passed/total | 合并前必须 100%（含 infra `check`） |
| **响应时间** | Trace `duration_ms`；可看 `retrieve_local` / `llm_synthesize` | 本地 Mock 路径给出本机 P50/P95；不设玄学 SLA |

说明：

- `run_eval.py` 当前主输出是 **passed/total**（全绿才 exit 0）  
- 分类命中率可在基线表中按 `category` 手工或脚本汇总  
- 响应时间优先从 `GET /api/runs` 或 Trace 导出，不与「是否答对」混成一个分数

## 7. 执行与基线归档

### 7.1 命令

```powershell
python scripts/run_eval.py
```

### 7.2 基线表模板

建议目录：`规范文档/eval-baselines/`（按次新增 md/csv）。单次记录至少包含：

| 日期 | git commit | passed/total | hit 率 | missing 拒绝率 | P50 ms | 变更说明 |
|------|------------|--------------|--------|----------------|--------|----------|
| 2026-07-16 | abc1234 | 20/20 | — | — | — | T0 文档冻结，评测未扩题 |

规则：

1. 每次优化 PR 附一行基线  
2. 失败 case **禁止静默删除**；应修代码或标 `skip` 并写原因  
3. 种子数据变化（换制度样例）必须在 notes / 基线备注写明  

### 7.3 与 CI

母本已含 `.github/workflows/eval.yml`：合并门禁以 `run_eval` 全绿为准。

## 8. 人工抽检（补充自动化）

自动化测「字符串与路由」；下列需抽样：

- 引用是否真指向相关段落（非标题碰巧命中）  
- 多轮是否语义连贯  
- 拒绝话术是否可操作（告诉用户下一步）  

抽检结果可简记在基线「备注」列。
